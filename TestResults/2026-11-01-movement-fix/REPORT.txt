BATTLETECH CO-OP 0.0.14: MOVEMENT FIX TEST BUILD
November 1, 2026

STATUS
Implemented and compiled; automated checks passed. Not yet verified in a running
two-player game. No deployment to the installed game or modification of saves.

CHANGES
1. New player movement commands are checked against the host's actor state before
   execution. An already-moved or finished actor cannot walk, sprint, jump or
   initiate another melee move. Guest input also performs the same preflight.
2. AttackInvocation is outside the movement guard. A normal move/jump does not
   consume firing or end the activation. Ace Pilot movement after firing remains
   available when the game reports that ability and movement is unspent.
3. Fixed an asynchronous UI handoff: the guest's original SelectionState is retained
   until its accepted invocation creates a sequence during replay. AssignOrders
   lets the game's normal completion handler transition from movement to firing.
4. Host IDs use G<sender>.<request> so this handoff does not depend on reply timing,
   other players' orders, or whether earlier requests were rejected.
5. Rejected selections recover on a subsequent idle update. Recovery does not clear
   a different unit's selection or a selection already waiting for an accepted move.
6. Version increased to 0.0.14, so both players must use the same build. Added logs
   for movement validation and 'bound selection to replay'.

EVIDENCE FOR THE UI FIX
Read-only inspection of the installed Assembly-CSharp.dll established:
- SelectionState.PublishInvocation subscribes to InvocationStackSequenceCreated,
  calls PublishMessage, and immediately unsubscribes. A later network replay
  therefore cannot reach this temporary subscription.
- SelectionState.IsComplete remains false when Orders is null.
- CombatSelectionHandler.RemoveCompletedItems advances a completed movement
  selection to AddFireState. Without its Orders reference, this path is skipped.
- OrderSequence.OnAdded sets HasMovedThisRound for movement-consuming sequences.
  AbstractActor.OnNewRound clears the movement flag. CanMove alone only checks
  operational/prone state, so it is insufficient to enforce one movement.
This identifies a concrete code-path defect. A live session is still needed to
confirm that it explains and resolves all observed symptoms in the supplied logs.

LIMITS
The tests do not run Unity, install Harmony patches into a live game, animate a
Mech, or drive the real HUD. They do not prove the complete gameplay sequence.
Attack eligibility, path legality, range and targeting rules remain the game's
responsibility; this is a movement guard, not a complete command validator.
Mod packs with alternative action rules remain unverified.
